## 一、优先确认的核心问题

这些问题是开发前必须优先解决的。没有确认前，接口、数据表、图表和权限都容易返工。

### P0-01：渠道 / 小组 / 平台的层级关系是什么？【已确认】

**已确认结论**

这是一个前端看板项目，当前展示层级确认如下：

```text
主管
├── 组长 / 小组 A
│   ├── 平台 A-1
│   ├── 平台 A-2
│   └── 平台 A-3
├── 组长 / 小组 B
│   ├── 平台 B-1
│   └── 平台 B-2
└── 组长 / 小组 C
    ├── 平台 C-1
    └── 平台 C-2
```

**看板展示规则**

- 组长视角：可以看到自己小组下各平台的信息，以及本小组的合计信息。
- 主管视角：可以看到各组长 / 各小组的信息，以及各小组的合计信息。
- 当前项目重点是前端看板展示，不先扩展成复杂组织管理系统。

**产品口径**

- “组长”是主管下的管理对象。
- “小组”是组长负责的数据范围。
- “平台”是组长 / 小组下面的二级统计维度。
- 主管端聚合维度：组长 / 小组。
- 组长端聚合维度：平台。

**仍需后续确认的边界**

- 一个组长是否只负责一个小组。
- 一个平台是否只能归属于一个组长 / 小组。
- 一个客户是否只能归属于一个平台。
- 一笔销售数据是否必须归属到唯一平台。

这些问题不影响前端看板第一层页面结构，但会影响后续数据清洗和指标归属。

**开发影响**

- 页面展示模块以 `项目框架.txt` 中各页面写明的模块为准，不做删减或重排。
- 主管页面展示维度：组长 / 小组。
- 组长页面展示维度：平台。
- 销售、客户、趋势、健康度、待跟进等模块都属于页面展示内容；开发可以在实现层复用计算逻辑和图表能力，但不能改变这些模块在页面中的展示职责。
- 数据接口需要支持按 `leader/group` 聚合和按 `platform` 聚合。

**甲方结论**

已确认：主管 → 组长 / 小组 → 平台。组长看本小组各平台和本组合计；主管看各组长 / 各小组和各组合计。

### P0-02：主管和组长的数据权限边界是什么？【部分确认】

**已确认结论**

看板层面的页面结构和数据可见范围已经明确。这里需要更正：主管端不是一个抽象的“各组组长展示页”入口，而是直接看到 4 个初始页面。

```text
主管端初始页面
├── 渠道总览页
├── 私域组展示页（页面集合 / 容器）
│   └── 包含：组别分析页 / 客户列表页 / 客户详情页
├── 达人组展示页（页面集合 / 容器）
│   └── 包含：组别分析页 / 客户列表页 / 客户详情页
└── 分销组展示页（页面集合 / 容器）
    └── 包含：组别分析页 / 客户列表页 / 客户详情页

组长端
└── 自己所属组的展示页（页面集合 / 容器）
    └── 包含：组别分析页 / 客户列表页 / 客户详情页
```

**页面口径**

- 主管：初始可见 4 个页面：渠道总览页、私域组展示页、达人组展示页、分销组展示页。
- 私域组展示页、达人组展示页、分销组展示页是三个明确的一级页面集合 / 页面容器，不是一个统一的“各组组长展示页”抽象入口，也不是单张叶子页面。
- 每个组展示页内部包含相同的子页面能力：组别分析页、客户列表页、客户详情页。
- 组长：只能看到自己所属组的展示页集合，以及该展示页集合内的组别分析页、客户列表页、客户详情页。
- 建议后续正式命名使用“组展示页”而不是“组长展示页”，避免把页面对象和人员角色混淆。

**权限口径**

- 主管端和组长端看到的页面集合不同，不能只靠前端隐藏菜单表达权限，路由层也要限制。
- 主管端：允许访问渠道总览页，以及私域组、达人组、分销组三个组展示页集合。
- 主管端：可以查看各组数据，包括各组展示页集合内的组别分析页、客户列表页、客户详情页数据。
- 主管端定位为查看角色，只负责看各组数据，不负责管理小组。
- 组长端：只允许访问自己所属组的展示页集合及其内部页面。
- 组长端：负责管理自己的小组。
- 组长端没有权限查看其他组展示页，也不应该通过修改 URL、切换参数等方式访问其他组数据。
- 组长端的数据范围必须锁定在自己的小组内，包括组别分析页、客户列表页、客户详情页。
- 在各自有权限的数据范围内，主管和组长均可查看全部字段，暂不做字段级差异权限。
- 业务负责人维度暂定保留，但后续可能删除，因此产品和前端都应将其视为可选维度，不要与核心页面结构强绑定。
- 账号来源后续设计后分发给主管和组长；第一版采用普通网页端账号登录 / 系统账号分发。
- 如果后续存在数据接口，组长的数据范围应由登录身份推导，不应信任前端传入的任意 `groupId`。

**网页账号方案口径**

第一版先采用普通网页访问方式：

- 系统提供网页登录入口。
- 账号由系统侧设计后分发给主管和组长。
- 账号需要绑定角色：主管 / 组长。
- 组长账号需要绑定所属组：私域组 / 达人组 / 分销组。
- 主管账号不绑定单个组，可以查看全部组数据。
- 第一版采用普通网页端账号登录 / 系统账号分发，避免依赖外部登录集成。
- 后续登录方式不再作为当前需求路径讨论。

**仍需甲方确认**

当前确认的是页面入口、看板聚合范围、基础权限边界和第一版登录方式，下面这些细项仍需要继续确认：

- 网页账号由谁维护和分发。
- 是否需要修改密码、重置密码、停用账号等账号管理能力。

**建议口径**

第一版看板建议控制为：

| 角色 | 初始页面范围 | 数据范围 | 字段权限 | 管理权限 | 聚合维度 |
| --- | --- | --- | --- | --- | --- |
| 主管 | 渠道总览页、私域组展示页、达人组展示页、分销组展示页 | 全部小组数据，包括各组组别分析、客户列表、客户详情 | 全部字段可见 | 只看数据，不管理小组 | 渠道总览按组聚合；组展示页内按平台聚合 |
| 组长 | 自己所属组展示页 | 自己小组数据 | 全部字段可见 | 管理自己小组 | 按平台聚合，并展示本组合计 |

补充：业务负责人维度暂定保留，但按可选维度处理。后续如果删除，不应影响页面主体结构和核心指标计算。

**开发影响**

- 前端路由应按固定组页面组织：`overview`、`private-domain`、`influencer`、`distribution`。
- 主管端和组长端应使用不同的导航配置：主管端展示 4 个初始页面，组长端只展示自己所属组页面。
- 三个组展示页是页面集合 / 容器，结构一致，应复用同一套组展示页布局，通过 `groupType` 或 `groupId` 区分私域组、达人组、分销组。
- 渠道总览页是主管独有页面，组长端不可见、不可访问。
- 组别分析页、客户列表页、客户详情页是组展示页集合内部的页面能力。
- 主管访问组展示页时可以指定目标组，并可以查看该组的组别分析、客户列表、客户详情数据。
- 组长访问时必须固定为自己所属组。
- 对组长端必须做路由守卫和数据范围限制，防止访问其他组页面或数据。
- 主管端只承担查看能力，暂不设计小组管理操作。
- 组长端承担自己小组的数据管理 / 查看范围，不能跨组。
- 暂不需要字段级权限控制，主管和组长在各自数据范围内均可查看全部字段。
- 业务负责人维度需要做成可选维度：筛选项、表格列、排序和图表维度都不应强依赖它。
- 接口查询需要支持主管总览聚合、指定组聚合、组长本人小组聚合三种访问场景。

**甲方结论**

部分确认：展示页是页面集合 / 容器，内部包含组别分析页、客户列表页、客户详情页；主管端和组长端页面集合不同；主管端 4 个初始页面和组展示页集合结构已确认；主管可以查看各组数据但只负责看；组长端管理自己的小组，只能访问自己所属组展示页，不能查看其他组；主管和组长在各自权限范围内均可查看全部字段；业务负责人维度暂定保留但后续可能删除；第一版采用普通网页端账号登录 / 系统账号分发；账号维护和分发细节待确认。

### P0-03：销售金额的统计口径是什么？【部分确认】

> 当前状态：平台计算方式暂挂。只有甲方后续提供或明确授权使用准确的平台数据后，才继续补充平台字段和过滤规则；当前不读取工作区其他数据文件。

**已确认结论**

销售金额指标在页面展示上拆为四类周期：

```text
销售金额
├── 昨日销售金额
├── 近7日销售金额
├── 近30日销售金额
└── 自定义时间销售金额
```

这里的“四类销售金额”是展示周期拆分，不是四套不同指标。底层仍然需要一套可复用的销售金额计算能力，然后根据不同时间范围聚合。

**当前模糊点**

不同平台的销售金额计算方式后续由甲方根据数据来源提供，因此当前不强行统一成单一金额公式。

需要后续按平台补充：

- 每个平台使用哪个日期字段作为销售日期。
- 每个平台使用哪个金额字段作为销售金额。
- 是否扣除退款、退货。
- 是否排除取消订单、未付款订单。
- 平台数据字段不一致时，如何映射成统一口径。

**需要甲方后续提供**

建议后续每个平台都按下面格式给计算方式：

```text
平台：待填写
销售日期字段：待填写
销售金额字段：待填写
订单状态过滤：待填写
退款 / 退货处理：待填写
备注：待填写
```

**建议口径**

第一版前端和指标层先统一抽象为：

```text
销售金额 = 平台侧标准化后的销售金额字段
销售日期 = 平台侧标准化后的销售日期字段

昨日销售金额 = 基准日前一天的销售金额合计
近7日销售金额 = 基准日前连续 7 个自然日的销售金额合计
近30日销售金额 = 基准日前连续 30 个自然日的销售金额合计
自定义时间销售金额 = 用户选择时间范围内的销售金额合计
```

平台原始字段进入系统后，需要先清洗成统一字段，例如：

```text
platform
sales_date
sales_amount
order_status
refund_amount
customer_id / customer_name
group_type
```

**开发影响**

- 页面展示周期已确定：昨日、近7日、近30日、自定义时间。
- 前端指标组件可以先按统一周期开发。
- 数据处理层必须预留“按平台适配计算规则”的能力。
- 不建议在页面组件里写平台差异逻辑，平台差异应在数据清洗 / 指标计算层处理。
- 同比、环比、趋势图都应基于标准化后的 `sales_date` 和 `sales_amount` 计算。

**甲方结论**

部分确认：销售金额展示周期已确认；不同平台的销售金额计算方式后续由甲方根据实际数据提供。

### P0-04：客户唯一标识是什么？

**当前模糊点**

文档大量以“客户名称”为跳转和统计对象，但客户名称不一定稳定，可能存在重名、改名、别名、合并等情况。

**需要甲方确认**

- 客户是否有稳定的客户 ID？
- 销售数据和客户名单是否能通过同一个客户 ID 关联？
- 如果只有客户名称，是否存在重名客户？

- 客户跨平台 / 跨小组时，按客户 ID 统一，还是拆成多个客户？

不建议直接用客户名称作为唯一主键。

**开发影响**

- 销售数据关联
- 客户详情页路由
- 客户去重
- 历史数据一致性

### P0-05：客户名单变动时，历史指标怎么计算？

**当前模糊点**

文档已经提到客户名单可能变动，但没有确定采用静态名单还是动态名单。

**需要甲方确认**

- 客户名单多久变动一次？
- 变动幅度大概是多少？
- 新增客户是否参与历史时间段统计？
- 删除客户是否仍保留历史销售记录？

客户指标 = 所选时间范围内的有效客户名单快照 + 销售事实数据

也就是：客户在什么时间属于哪个小组、哪个平台，需要有历史记录。

**开发影响**

- 客户名单快照表

- 历史统计是否可追溯
- 客户数、未拿货客户数、活跃客户数、沉默客户数

### P0-06：活跃客户、沉默客户、未拿货客户如何定义？

**当前模糊点**

客户指标中包含：

- 客户总数
- 有拿货客户数
- 未拿货客户数
- 活跃客户数
- 沉默客户数

但这些状态可能互相重叠。

**需要甲方确认**

- 有拿货客户：是在所选时间范围内有拿货，还是历史上有过拿货？
- 未拿货客户：是从未拿货，还是所选时间范围内未拿货？
- 活跃客户：近多少天有拿货算活跃？
- 沉默客户：近多少天未拿货算沉默？
- 新增但尚未拿货的客户，算未拿货还是沉默？

## 五、页面展示模块保留原则

`项目框架.txt` 中各页面写明的模块，是甲方要看的展示部分，不是开发可以随意合并、删除或后置的模块。

### 5.1 主管端展示模块

主管端包括：

```text
渠道总览页
私域组展示页
达人组展示页
分销组展示页
```

其中各组展示页是页面集合 / 容器，内部包含：

```text
组别分析页
客户列表页
客户详情页
```

页面内原始设计的展示模块需要保留，例如：

- 销售指标。
- 客户指标。
- 趋势指标。
- 健康度总览指标。
- 待跟进提醒。
- 客户列表。
- 客户详情。

### 5.2 组长端展示模块

组长端只能看到自己所属组的展示页集合，展示页内部仍包含：

```text
组别分析页
客户列表页
客户详情页
```

其中 `项目框架.txt` 中写明的各类模块，是组长需要看到的页面内容，后续只补充口径，不改变模块归属。

### 5.3 开发实现边界

开发侧可以做复用，但复用只发生在实现层：

- 可以复用时间规则。
- 可以复用数据清洗逻辑。
- 可以复用指标计算函数。
- 可以复用图表组件。
- 可以复用表格组件。

但这些复用不能改变产品展示结构：

```text
产品展示模块 = 按甲方页面设计保留
开发实现组件 = 在不改变展示模块的前提下复用
```
